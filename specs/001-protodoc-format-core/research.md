# Protodoc: Research and Options Considered

Status: APPROVED (Eyvar, 2026-09-07) | Spec ID: 001-protodoc-format-core | Phase: 3 (plan) | Date: 2026-09-05

This file is the permanent record of what was tried, why it was rejected, and what evidence supports the rejection. Its purpose is narrow: no tradeoff recorded here should ever need to be re-argued from scratch. If a future contributor proposes zip, protobuf, offset-based spans, a hash-chained op log, or AV1, the answer is in this file, with the requirement ID it violates and the concrete failure mode.

The chosen base for phase 3 is **Protodoc Ledger (PDL), Repair Set 2**: a fixed 1,048,576-octet prefix (header, self-digesting commit ring, frontmatter, segment table, integrity block) followed by an append-only ledger of immutable, single-typed sealed segments, with canonical octets defined as a function of state rather than of the file's own bytes. Everything below explains how that shape was arrived at and what else was tried.

---

## 1. Method

Five candidate architectures were drafted from five distinct priors (a database or file-format tradition each was rooted in, not a shared starting template). Each was scored independently against three adversarial judging lenses:

1. **Canonical octets, determinism and integrity**: does the design actually produce one octet sequence per document state, computably, with no undefined free parameter, across two independent implementations.
2. **Write cost, partial access and size**: does the arithmetic in NFR-008, NFR-009, FR-055, FR-057 and NFR-032 actually close at the stated document-size ceilings, or only at the sizes the architecture chose to show its own math for.
3. **Adversarial security and verification**: signature coverage, redaction hiding, parser/verifier differentials, decoder-before-verify ordering, and allocation/ceiling attacks, run against the design as an attacker would read it, not as the author intended it.

Each lens produced a 1-6 score, a verdict (`viable-with-repair` or `fatally-flawed`), a list of `fatal_flaws` (each with the exact claim attacked, why it fails, the requirement violated, and whether it is repairable), and a `steal` list of mechanisms worth carrying forward regardless of which architecture won.

After scoring, the design synthesized from the winning base was itself put through three **refutation angles** aimed at the whole, not at any one component: implementability under CP-002/CP-003/CP-010, two-implementation divergence (would two independent teams following the prose produce different canonical octets or different verdicts), and thirty-year survival (crypto aging, registry dependence, the incentive for a second implementation to ever get built). All three angles refuted the prior draft (Repair Set 1) with concrete kill shots. **Repair Set 2**, which this plan describes, is the response: every kill shot that attacked a specific, nameable algorithm or constant is closed by naming that algorithm or constant; every kill shot that attacked something outside architectural authority is recorded as a flagged conflict or an escalation to governance rather than silently designed around. See Section 8 for the itemized disposition of all sixteen kill shots.

PDCS is marked with one **unrepairable** finding: NFR-032/NFR-033's at-rest and load-ratio ceilings are permanently, not merely conditionally, violated by an ordinary scattered single-character-edit trace under PDCS's identity design, with no compaction-based repair available because re-basing would detach every anchor built on the affected identities (a violation of HC-011's preservation-across-edit guarantee). Anvil is marked **fatally-flawed** on the adversarial security lens: its double-buffered superblock is the unsigned, attacker-recomputable root of trust for which physical state a reader opens, and the design's own reader rule ("take the surviving slot with the higher sequence number") has no defined tie-break for two self-valid slots at equal sequence numbers, which is a verifier-versus-installer split of exactly the kind FR-104's rationale names, reproduced by construction.

## 2. Container framing

The container question (DP-001) is which physical byte layout the whole format sits on. The origin sketch proposed protocol buffers over a zip-of-parts container. Neither survived; both are recorded here as permanently rejected, in enough detail that re-proposing either is answered by this section alone.

### Zip-of-parts (origin sketch), REJECTED, fails independently on six requirements

Zip is the incumbent shape every candidate architecture tested itself against, because it is the shape the origin sketch assumed. Every one of the five architectures independently rejected it, for the same reasons, evidenced from different angles:

- **Content-independent identity window (HC-006, FR-006/007).** Zip's first octets are a local file header whose name and sizes are content-derived. There is no fixed, content-independent 512-octet identity window; a reader cannot determine format identity, document class or major version without already having parsed writer-chosen, content-dependent bytes.
- **Bounded random access (HC-005, FR-055).** The manifest (central directory) is at the end, located by a backward scan for the end-of-central-directory record. That record carries a variable-length comment field, so the candidate set for "where is the real EOCD" is unbounded, and two conforming parsers can select different records for a crafted file. This is not hypothetical: it is the documented mechanism behind a real verifier-versus-installer signature bypass (cited across multiple architectures' adversarial lenses as the 2013 mobile-platform case). FR-055's 3-dependent-read, a-priori-known-anchor requirement is unreachable from a trailing, scan-located structure.
- **Bounded write cost (HC-003/HC-004, NFR-008/009, FR-056/058).** Saving rewrites the central directory in full and shifts every subsequent local-file-header offset. An edit anywhere in the file relocates every byte downstream of the touched entry. This directly violates the requirement that untouched extents stay byte-identical across an edit and that novel chunks under content-defined chunking stay bounded by the edit size, not by document size.
- **Opaque token identity (HC-012, CON-008).** Zip entry names are path-like strings with case-sensitivity mismatches across platforms, which is exactly the mechanism behind the archive-traversal and duplicate-part-under-one-name attack classes (the "one package holds two entries for one part" bypass). CON-008 bans hierarchical, path-like, case-folding identifiers outright; zip cannot be retrofitted to avoid this without abandoning entry names as the addressing mechanism, i.e. ceasing to be zip.
- **No-op-save octet identity (HC-002, NFR-001/003).** Per-writer extra fields, timestamps, entry ordering and DEFLATE compression level are all encoder-chosen and unspecified by the zip format itself. Two conforming zip writers, or the same writer at two different times, legitimately produce different bytes for identical logical content, which makes NFR-003's "open-and-save-with-no-edits is octet-identical" requirement permanently unreachable without a from-scratch profile that is no longer recognizable as zip.
- **Total, zero-slack octet accounting (HC-015).** Zip permits unaddressed gaps, prepended octets before the first local header, and data-descriptor slack whose contents are unspecified by the standard. HC-015 requires every octet in the file to be mechanically classifiable as acted-upon or not; zip's permitted slack regions make that classification impossible, which is precisely the appended-unsigned-octets attack class FR-063 exists to close.

**Verdict: rejected outright, no repair path.** A "restricted zip profile" that closed all six holes would no longer interoperate with any real zip reader and would carry all of zip's incidental complexity (DEFLATE, entry model, central directory) for none of its benefit. This was not treated as a live design point past the initial framing.

### Fixed 1,048,576-octet prefix plus append-only sealed-segment ledger (PDL), CHOSEN

Layout: `Header[0,512)` frozen at `[0,32)` forever, `CommitRing[512,4096)` (7 self-digesting 512-octet slots), `Frontmatter[4096,262144)` (preview + metadata), `SegmentTable[262144,1048960)` (16,384 ordinal-indexed 48-octet slots, the sole inventory), `IntegrityBlock+UnitIndexRoot` to `1,048,576`, then an append-only ledger of immutable, single-typed sealed segments.

**What it buys:** the three nested prefix budgets (512 / 262,144 / 1,048,576 octets, per HC-006/HC-007) land exactly on region boundaries with zero slack, so TR-006/007/008's bounded-prefix determinations (type, length, digest, coverage, inertness) never require a scan or a discovery step; storage ordinals are monotonic and independent of content, so HC-012's storage-order-independent-of-digest requirement holds by construction; sealed segments are never rewritten, so FR-056/058's untouched-extent and zero-relayout guarantees hold by construction, not by writer discipline; a 7-slot self-digesting commit ring gives FR-117's crash-atomicity without a sidecar journal, temp file or rename, because torn writes only need to be *detectable*, not prevented.

**What it costs:** every document pays a flat 1,048,576-octet floor regardless of content size (a 200-octet note costs a megabyte; the unused prefix is a normatively-defined zero fill, so the real cost is paid only on naive, non-deduplicating filesystems, but that is where most documents live). The segment table is capped at 16,384 slots, which under continuous autosave exhausts in roughly 58 days of active editing on a *signed* document, and NFR-004 refuses compaction outright whenever a signature is present, which was, before Repair Set 2, capable of permanently bricking an actively-edited signed document (residual risk, see Section 8). Superseded content extents accumulate between explicit compactions with no automatic reclaim.

**Verdict: chosen, with two structural repairs made in Repair Set 2** (partial compaction restricted to segments outside any signature's covered ranges, and structure_digest redefined to be placement-insensitive so partial compaction cannot invalidate a signature). See Section 5.

### Content-addressed object graph in a slotted, dual-buffered slab (Slab-DAG), REJECTED as base, mechanism partially adopted

Every component stored under the digest of its own octets; structure is a DAG of digest references; the file is a slab holding those objects, distinct from both the object graph and the canonical form. Its central claim, that the state root is a pure function of state so signature coverage is total by construction, is the single mechanism PDL grafted into its own signature design (`T_C_root` signed directly, see Section 5).

**What it cost, as scored:** the equivalence class (what counts as "the same state at rest") is self-contradictory as specified: clause (iv) of the design's own formal equivalence relation makes a compacted file and an uncompacted file of the same logical content *not* equivalent (different SLACK-row counts), which directly breaks the design's own worked example claiming they are (fatal-severity finding on the determinism lens, repairable in principle but never actually reconciled in the Slab-DAG draft). Its canonical DEFLATE encoder for writer-generated rasters left the greedy-matcher's hash-chain insertion policy and collision behavior unspecified, which is exactly the kind of encoder freedom that produces byte divergence between two independent implementations building the same preview thumbnail. Under the adversarial lens: the superblock's `arena_tails`/`region_lens` fields are claimed to be "a pure function of state" in one place and required to vary across equivalence-class members (to allow append-only growth) in another; both cannot be true, and A-ACTED (the audit that must classify every octet as acted-upon or not with zero cross-implementation divergence) cannot be satisfied over a set whose own definition contradicts itself. Separately, its SLACK inventory entries are simultaneously claimed to be committed by the state root and provably underivable from it (SLACK is by definition unreachable from the root), which reproduces the "verifier trusts an inventory it never re-derives" class of bug TR-009 exists to close.

**Verdict: rejected as the base**, its coverage-by-construction insight kept as a graft.

### Typed chunk stream, PNG-shaped framing over a fixed prefix (PDCS), REJECTED, one unrepairable finding

Flat, append-only sequence of PNG-shaped typed frames (length, type with criticality bits, payload, CRC-32) behind the same class of fixed-offset prefix as PDL, sized to a 16,000-stored-unit ceiling.

**What it cost:** because PDCS's text-block frames are whole, atomically-sealed units with no intra-frame patch mechanism, and its inventory ceiling forces large multi-paragraph frames on any large document, a one-word edit inside a large frame must append and zero out the *entire* frame, which the design's own worked arithmetic shows can run roughly 32x over both NFR-008's and NFR-009's write and novel-chunk budgets at the document's own stated size ceiling. Compounding this, because NFR-004 refuses compaction on any signed document, every edit's zeroed-out superseded frame becomes permanent, unreclaimable growth for the life of the signature. Most decisively: PDCS's identity design produces the correct 0.60-octets-per-character cost only at long average run lengths, and the design's own known-weaknesses section admits that an ordinary editing pattern (scattered single-character insertions, which arise naturally from retyping, autocorrect, or merge-conflict resolution, not only from an adversary) produces one run per character at roughly 20x text size, with **no repair path**: compaction cannot re-base runs because doing so would change every affected character's identity and detach every anchor built on it, which HC-011 forbids outright. This is the one finding across all fifteen lens evaluations marked **unrepairable** rather than merely fatal, because the fix (re-basing) is independently forbidden by a different hard constraint.

**Verdict: rejected.** PDCS's PNG-style outer framing (fixed-width length, no nested containment) was noted as a clean idea but was superseded by PDL's own fixed-slot-array approach, which achieves the same "no cascading length-prefix rewrite" property without inheriting PDCS's frame-granularity write-amplification problem.

### Copy-on-write Merkle-B-forest, transactional embedded store (Anvil), REJECTED, fatally-flawed on the security lens

Pages linked by (offset, length, digest) pointers rather than inline nesting, committed by flipping a double-buffered superblock, with a write-ahead redo slot protecting the one region (the front inventory) that cannot be pure-append.

**What it cost:** the double-buffered superblock is protected only by its own unkeyed self-digest, which any attacker can recompute, and the reader-selection rule ("take the surviving slot with the higher sequence number") has no defined behavior for two self-valid slots sharing the same sequence number, an outcome the design never forbids at the wire-format level. Two conforming implementations can pick different slots and render different, both-signed-looking documents from one file, reproducing the 2013 verifier-versus-installer split by construction. Separately, because the current-state pointer must change on every edit while FR-066 forbids re-signing, the pointer that determines which content a signed document currently presents is structurally unsignable in this design, and an attacker can append arbitrary content past the last valid offset, bump the sequence number, recompute the (unkeyed) self-digest, and have the file render attacker content while a prior, legitimate signature still verifies over the untouched original state. This is the appended-incremental-update attack class named directly in FR-063's own rationale, reproduced rather than closed. A third, independent fatal finding: pointer-based nesting with content-address-based deduplication permits a page to be referenced from more than one parent, and nothing bounds in-degree per state, so a small number of nodes (roughly 60, doubly-referencing their predecessor) produce an acyclic reference graph that nonetheless requires walking on the order of 2^60 leaves during canonicalization, Merkle computation, and extraction, which is the exact "roughly 281 TB from a 10 MB input" exponential-expansion construction FR-106's own rationale names and that the design's cycle-detection pass (which only rejects genuine cycles, not exponential DAG fan-out) does not catch.

**Verdict: rejected.** The write-ahead redo-slot idea (bounding a from-scratch WAL protocol to exactly the one region that structurally cannot be pure-append) was noted as a clean, narrowly-scoped mechanism worth remembering, but is not adopted because PDL's self-digesting commit ring achieves crash atomicity for the whole prefix without needing a WAL at all.

### Immutable base plus delta generations (Stratum), REJECTED

Generation 0 is an immutable content-addressed base; each commit appends exactly one bounded delta generation; compaction is an explicit generation-merge, refused while any signature is present.

**What it cost:** the design permits (and its own container section names) a reserved-but-unenforced header padding field with no stated normative fixed value, which is exactly the ambient/uninitialized-octet class NFR-005 exists to close. Its canonicalization rule sorts some unordered tables (style, language, font) by their own digest-derived CID, which directly contradicts CQ-007's requirement that canonical storage order never depend on a digest, an unforced, self-inflicted violation since a reading-order-of-first-use rule would have been equally simple. Under the adversarial lens, its Merkle leaf-commitment formula hashes only a component's payload octets, leaving the inventory record's own CID, kind, and normative/derived flags outside every digest and every signature: swapping the CID fields of two same-kind inventory records, or flipping one kind byte, leaves every leaf commitment and the Merkle root unchanged, so a validly signed document can be made to resolve every reference to different content, or dispatch payload octets to a different kind's interpreter, while the signature still verifies and the signer's identity is displayed. Separately, its leaf and internal-node commitments are truncated to 128 bits "for space," which drops birthday-collision resistance to 2^64, a figure within reach of purpose-built hardware; this breaks both the general integrity claim and the specific binding property the redaction commitment depends on for hiding.

**Verdict: rejected.**

### Other DP-001 candidates rejected without a full architecture built around them

- **Page-oriented file with a fixed-size page table (SQLite/ext-style), extents allocated by page.** Rejected because a page allocator's free list is exactly the kind of reclaimable-hole-carrying-prior-octets residue HC-019 forbids in published output, and page relocation on content change breaks FR-058's placement-independent-of-content rule.
- **Front pointer to a back-placed current inventory** (fixed header, but the inventory itself lives at the tail with only a pointer up front). Rejected because it abandons TR-006 through TR-008's bounded-prefix determinations outright (a scanner reading only the fixed prefix cannot enumerate stored units, coverage, or inertness) and spends one of FR-055's three dependent reads on discovering the inventory before it can even begin locating a unit.
- **Trailing index or trailing central directory appended per save** ("put the index at the end so it can be appended," the shape every append-only design's own instincts reach for first). Rejected for the same reason as zip's central directory and PDL's own front-pointer alternative: TR-006/007/008 require the full inventory in the *leading* window, not the trailing one, and NFR-012's extraction budget forbids a whole-file pass before the first character is emitted.
- **Single flat length-prefixed message tree (protobuf-as-container).** Rejected because nested length-prefixed containment means editing a leaf rewrites every ancestor's length prefix and shifts the entire contiguous encoding downstream, a direct and structural violation of HC-004/NFR-009 with no repair short of abandoning nested framing, which is discussed at length under Section 3.

## 3. Byte encoding

### Protocol buffers (origin sketch's proposal), REJECTED, the canonical-serialization problem stated precisely

Protocol buffers were the origin sketch's proposed wire encoding for structural (non-payload) data. Every one of the five candidate architectures independently rejected it, and the rejection is precise enough to record as closed:

1. **No canonical serialization is guaranteed by the format itself, and this is documented by proto3's own maintainers, not inferred.** Deterministic serialization mode is stable only within one build of one binary; it is explicitly not canonical across languages, and is documented to become unstable across builds once unknown fields are present, because unknown bytes-typed fields and unknown nested-submessage fields share a wire type, so an unknown-field set cannot even in principle be canonicalized without knowing its schema. HC-002's requirement (exactly one legal octet sequence per value, with signature/timestamp/redaction-salt components carved out as the only permitted non-determinism) is therefore not something a "sufficiently disciplined" protobuf writer can satisfy: the ambiguity is a property of the wire format, not of writer behavior.
2. **Non-minimal varints are legal and must be accepted.** A reader that rejects them is non-conforming to protobuf itself; a reader that accepts them admits multiple octet sequences per integer value, which is exactly the kind of malleability CON-005/HC-009's "at most one normative representation per value" rule exists to forbid.
3. **Packed versus unpacked repeated scalar fields are both legal for one logical repeated field**, a second, independent source of multiple valid encodings for one value.
4. **Field ordering within a message is unspecified**, a third independent source of encoding freedom that CON-005 forbids.
5. **Map serialization order is documented by Google as non-deterministic**, and protobuf's map type therefore cannot appear anywhere a canonical form is required (this is also why the chosen encoding bans maps outright and uses sorted vectors instead; see below).
6. **float and double field types exist and are the natural type for geometry**, which is incompatible with CON-012's requirement that every persisted geometric value be an exact integer multiple of a 1/914400-inch base unit with no binary floating point anywhere in the schema.
7. **Recursion depth and message-size limits are library defaults**, which CP-007 forbids: every ceiling in Protodoc must be a normative, decimal-integer, CI-checked constant, never a library's own choice.
8. **Unknown-field retention across a round-trip is a library-version property, not a specified guarantee.** This reproduces, verbatim, the silently-discarded-unknown-fields failure that FR-017 exists to prevent, and it means unknown fields (which is exactly the shape forward-compatible extension payloads need) carry no disposition, no fallback, and no digest of their own; HC-013's extension envelope needs all three sitting *outside* the payload's own schema, which protobuf's unknown-field mechanism cannot provide.
9. **The nested-message model is nested length-prefixed containment**, so editing a leaf value rewrites every enclosing message's declared length and shifts the entire contiguous byte stream downstream of the edit. This is a direct, structural violation of HC-004/NFR-009's bounded-novel-chunk requirement, and it is not fixable by any writer discipline: it is the model itself.
10. **Generated protobuf parsers construct typed objects and allocate memory from declared repeated-field and length counts as they parse**, which is precisely the boundary HC-008/NFR-034 forbids (allocation from an unvalidated declared value, decoder construction before verification).
11. **A shared `.proto` schema compiled by both conformance implementations is shared source code.** CP-003 requires two implementations "sharing no source code" as the stability gate; a compiled-from-one-schema pair of parsers defeats that gate by construction, independent of every wire-format issue above.

`protoc` 35.1 being installed on this machine is a fact about tool availability, not a design decision; it does not change any of the eleven points above. **Verdict: rejected outright, no partial-adoption or restricted-profile path was found that survives points 9, 10 and 11 without ceasing to be protobuf.**

### Other encodings considered and rejected

- **Deterministic CBOR (RFC 8949 section 4.2 core deterministic encoding profile).** The closest runner-up. Closes integer minimality and map key ordering, but leaves float encoding, indefinite-length items, and an open tag registry as residual freedoms that still require a closing profile to be written, and remains self-describing at the type level (an integer is expressible as major type 0 or as a tagged bignum, a string as definite- or indefinite-length), which is itself a second-representation surface CON-005 exists to close. Closing every remaining freedom leaves a worse, more complex TLV grammar than a from-scratch one, while adding a large normative external reference against CP-002's per-role statement budget. Rejected.
- **ASN.1 DER.** Genuinely canonical (its one-encoding-per-value discipline is exactly what the chosen grammar borrows), but requires a schema language and a code generator whose output CP-010 requires be reviewable in-repository; its variable-width length encoding defeats fixed-offset in-place patching; and BER-versus-DER acceptance drift is a documented, real-world parser-differential source. Rejected as the primary grammar, though its "exactly one legal encoding" discipline is the direct ancestor of the chosen PDL-VARINT rule.
- **FlatBuffers / Cap'n Proto arena layout.** Zero-copy access is attractive against the 3-dependent-read budget, but both admit multiple valid layouts for one logical value (vtable sharing, field ordering within a table, unspecified padding contents), which HC-002 kills outright; both encode child locations as offsets embedded in the data, which is hazardous under HC-010's ban on persisted counted positions; and neither format specifies a canonical form at all, by its own designers' admission. Rejected.
- **EBML / Matroska framing.** Instructive as a negative result from within the typed-chunk-stream family itself: RFC 8794 mandates shortest-length encoding for Element IDs but explicitly does *not* mandate it for Element Data Size, permitting the same integer to be encoded at 1, 2, 3 or 4 octets so a writer can pre-reserve space and overwrite the size later. That is a documented, standards-body-acknowledged multiple-encodings-per-value hazard, which HC-002 forbids outright. Its master-element nesting is also length-prefixed containment, the same HC-004 failure mode as protobuf. Rejected; PNG's fixed-width, non-nesting chunk framing was preferred wherever a PNG-shaped outer layer was tried instead.
- **Fixed-width structure-of-arrays with no self-description at all (POE / PRE in the PDCS and Anvil drafts).** Achieves exactly-one-encoding-per-value by removing every choice (no varints, no optional fields, no floats, fixed width per field by table lookup), which is the right idea for the parts of the format that are genuinely fixed-shape, but applied *universally* it inflates the kind registry into dozens of frozen field tables (61 in one draft) because every "sometimes present" variation must become a distinct kind or a counted 0-or-1 list, which works directly against CP-002's per-role normative-statement ceiling. Adopted only for the physically fixed-offset prefix regions (header, commit ring, segment table), not for segment frame content.

### Chosen: a two-layer hybrid, split by mutation frequency

The chosen encoding makes the split explicit rather than picking one grammar for the whole file, because the two regions of the file have opposite needs.

**Layer 1, raw fixed-layout structs at fixed byte offsets** (header, commit ring, segment table slots): zero tags, zero self-description, offsets computed by pure arithmetic on an ordinal. Chosen because HC-006/HC-007 require zero-parse, content-independent access to these regions, and because these are the only structures ever patched in place, where a self-describing tag-length-value grammar would add nothing but parsing cost. The layer boundary rule is mechanical: a structure is Layer 1 if and only if it is written more than once in a document's life; everything written once and sealed uses Layer 2.

**Layer 2, PDL-TLV, for every segment frame payload:**
- Field tags: 1 octet, scoped per record-type schema, a permanent ceiling of 256 fields per type, tags strictly ascending, a reader rejects any out-of-order or duplicate tag rather than accepting it.
- Integers and lengths: **PDL-VARINT**, adopted verbatim from Bitcoin Core's CompactSize varint (a 15-year, battle-tested, fully closed grammar with zero remaining free parameters): 1 octet for values 0-252; a marker octet of 253, 254 or 255 followed by exactly 2, 4 or 8 big-endian octets for wider values; any non-minimal encoding (for example, encoding 100 with the 2-octet form) is rejected, closing the length-of-length regress that an earlier draft of this same grammar left open (see Section 8's account of the two-implementation-divergence refutation).
- Sorted vectors: compared by unsigned byte-lexicographic order over the *full encoded octets*, never over a decoded value; key/value pairs sorted by key octets only.
- Repeated values: exactly one legal form, a count-prefixed sequence. No packed-versus-unpacked choice exists because there is only one shape.
- No floats, ever, anywhere in the grammar. No maps, ever; every keyed association is a sorted vector, closing protobuf's and CBOR's map-ordering ambiguity by removing the construct rather than specifying an order for it.

This closed grammar is itself a direct repair made in Repair Set 2: the refutation angle on two-implementation divergence found that an earlier draft named only six *closure properties* of PDL-TLV ("minimal-length integers," "no defaults," etc.) without ever giving an actual byte grammar, leaving tag width, the length-of-length encoding, and the sorted-vector comparator all unspecified and therefore free to diverge between two independent implementations on the very first encoding pass. See Section 8.

## 4. Identity and anchoring

### Why the origin sketch's offset-based spans were rejected: the concurrent-edit argument, in full

The origin sketch proposed style spans addressed by `(start offset, length)` pairs, counted from the beginning of a text sequence, the conventional representation in essentially every prior word-processor and layout format. This is CQ-001 option B/C territory, and it is rejected outright by CQ-001/CQ-002's resolution (identity anchors only; counted positions illegal in persisted form) and by HC-010 (no persisted construct may locate a position by a count of text units from the start of a sequence). The reasoning, stated fully rather than by citation alone:

An offset is only a stable name for a character while nothing before it in the sequence changes. The moment any other author, anywhere else in a concurrently-edited document, inserts or deletes a single character upstream of the offset, every offset downstream of that edit now names a *different* character than the one the annotation, comment, cross-reference or formatting span originally pointed at, even though the span's own content did not move and was never touched. This is not a corner case: it is the ordinary, expected condition of any document under real multi-author editing, and it is the condition FR-092 through FR-096 and HC-026 are written to test at scale (1,000 random delivery permutations of a 5-author, 20,000-operation trace, requiring identical resolved state across two independent implementations regardless of delivery order).

Concretely, the failure modes an offset-based design cannot avoid:
- **Anchor drift under concurrent insertion.** Two authors editing offline, one inserting 40 characters before paragraph 3, the other adding a comment anchored at what was offset 500 in paragraph 4. When the edits merge, offset 500 in the merged document is a different character than the one the comment was anchored to; the comment silently attaches to the wrong text, with no way to detect that this happened, because the offset itself carries no information about which state it was computed against.
- **No stable identity across split, merge, move and reorder** (HC-011's explicit list of operations that must preserve identity). An offset is a property of a document's current linear layout; splitting a paragraph, moving a table, or reordering sections all change every offset downstream of the operation, so any construct addressed by offset must be actively repaired on every one of these operations, and the repair itself requires knowing, at the moment of the structural edit, every offset-addressed construct that might be affected, an unbounded, whole-document-scanning obligation that reintroduces exactly the "editing a leaf shifts everything downstream" cost HC-004 was written to forbid, except now paid by application logic instead of by storage.
- **Interleaving under concurrent insertion at one point.** Even setting aside cross-reference drift, an offset-addressed *sequence itself* (the text, if positions were the merge mechanism) has no way to guarantee that one author's contiguous typed passage survives as an unbroken substring when another author types at the same point concurrently; this is exactly the failure mode published analyses of RGA, Logoot and LSEQ document (see Section 6), and it is a property of counted, orderable positions generally, not of any one implementation's bug.
- **No collision-free minting under CQ-004's non-determinism constraints.** An offset is derived entirely from surrounding content, so it cannot double as a persisted identity minted once and preserved forever the way HC-011 requires; a construct that needs both a position (for merge ordering) and a durable identity (for anchoring) cannot get both properties from one integer.

The origin sketch's design additionally combined offset-based spans with protobuf and zip, meaning an edit's shifted offsets would have compounded with zip's shifted central-directory entries and protobuf's shifted nested-message length prefixes: three independent sources of "one small edit relocates everything downstream," stacked. This is recorded as the clearest illustration in the whole research record of why intent-before-mechanism discipline matters: the origin sketch's three components were each individually defensible in isolation (offsets are how every legacy format does it; protobuf is Google's general-purpose default; zip is a familiar container) and catastrophic in combination against this exact spec's requirements.

**Verdict: rejected outright.** No repair (bounded offset ranges, periodic offset re-basing, offset-plus-checksum) was found that avoids reintroducing either a whole-document scan on every structural edit or a return to counted positions in a different disguise.

### Chosen identity representation and rejected alternatives (DP-003)

**Chosen: a fixed-width, 128-bit CSPRNG-minted token per contiguous typing burst ("run"), with character identity = `(run_id, base_ordinal + i)`.** Runs merge under a pure syntactic predicate (adjacent, equal style, contiguous ordinals) with no actor/session/clock component anywhere in the construction. Collision probability is bounded below 2^-60 at up to 2^34 mints per lineage, giving roughly 1.5e-23 at the spec's own 10^8-mint/1,000-replica conformance scale (FR-023).

Rejected alternatives, with the specific requirement each one fails:

- **Fixed-width opaque token per character, stored explicitly, one per character.** Blows NFR-032's 2.0x at-rest ratio and NFR-033's 1.5x load-time ratio by roughly an order of magnitude; 16 octets per character is 16x the raw text size for Latin content with no run-merging available to recover it.
- **Hash-derived identity: digest of `(minting nonce, parent identity, ordinal)`.** Verifiable and compressible, but the ordinal component is a position within the parent whose meaning depends on the parent's *current* set of children, which is precisely the counted-position shape CON-001 forbids; rebasing a subtree to repair fragmentation would also change every descendant's identity, violating FR-020's preservation-across-move-and-reorder guarantee.
- **Actor identifier plus counter (the conventional CRDT construction).** Rejected twice over: FR-023 bans any value derived from actor identity, device identity, wall-clock time or editing session in the minting construction itself, and separately, FR-080's mandatory identity-strip-on-publish would remove the actor/site component from every identifier at once, detaching every comment, suggestion, and cross-reference in the document simultaneously the moment it is published.
- **Document-scoped monotonic counters.** Collide across forks on exactly the legitimate cross-fork merges FR-019 requires to succeed; two independent forks each issuing their own counter starting from the same base will mint duplicate identifiers for unrelated content.
- **Dense-space (fractional/logical-clock) position identifiers, Logoot- or LSEQ-style.** These remain ordered, counted positions in a shared coordinate space by construction, directly banned by FR-025/CON-001 regardless of the coordinate space being dense rather than integer; and published results (cited across three independent architecture drafts) demonstrate that even the improved dense-identifier families interleave concurrently-typed passages under reverse-direction (backspace-style) concurrent insertion, failing HC-026/FR-093's non-interleaving requirement on top of the position-identity violation.

### The run-internal-ordinal-versus-counted-position tension (TN-003), and how it is closed

Run-merging, the mechanism that makes per-character identity affordable at all, stores a character's identity as a run base plus an offset *within that run*. Read carelessly, that offset looks exactly like the counted position CON-001 forbids, and the approved spec text does not draw the line between them anywhere. This is TN-003, and it is closed in this plan by a mechanical, second-implementer-checkable discriminating rule rather than by a judgment call: **a persisted integer is a forbidden counted position if and only if its correct interpretation depends on the stability of content *outside* the single immutable value it indexes into.** A within-run offset indexes into an immutable minting event (the run's own text, fixed at mint time and only ever split, never renumbered from the front); its correctness does not depend on anything happening elsewhere in the document. A hypothetical "character number 500 in the document" does depend on everything before it, which is exactly the property CON-001 forbids. This rule is stated normatively as the A-FIELD-ROLE audit's discriminating clause, using a closed, 7-tag field-role vocabulary (IDENTITY-COMPONENT, PHYSICAL-OFFSET-OR-LENGTH, ORDINAL, DIGEST, ENUM, SCALAR-VALUE, COUNT) with the explicit rule that a field tagged IDENTITY-COMPONENT (which includes `base_ordinal`) may be compared and looked up but never used for positional arithmetic counted from a sequence start; only reader-computed, non-persisted scalar positions may be used that way. This rule, and the closed role vocabulary it belongs to, is itself convergent: two independent architecture drafts (Slab-DAG's "no POSITION role available to declare" and Stratum's near-identical discriminator) arrived at the same shape independently, which is treated as corroborating evidence rather than coincidence.

## 5. Integrity, signature and redaction constructions

### Two-tree structure, chosen, with two normative gaps closed in Repair Set 2

`T_S` (storage-integrity tree, arity-16/depth-4 over the fixed 16,384-slot segment array, signature-independent) and `T_C` (content-commitment tree, aligned to content-subtree boundaries, carrying per-subtree salted redaction commitments) are kept as two separate structures with two separate jobs, rather than one tree serving both (the alternative FR-104/FR-105 explicitly forbid, because a storage-integrity structure and a content-commitment structure disagreeing with each other, with no defined precedence rule, is the exact two-inventories-disagree bypass class the 2013 mobile-platform incident demonstrates). Every internal node in either tree hashes `tag || 16 x 32-octet slot`, always exactly 16 slots regardless of actual child count.

Two things were left unspecified in the pre-repair draft and are closed here:

1. **The absent-child filler value.** Neither tree previously stated what octets get hashed into a slot for a child that does not exist, which is the common case since neither tree's occupancy is ever an exact power of 16. Left unspecified, one implementation zero-fills, another shortens the hashed buffer, a third invents its own sentinel, and each produces a different internal-node digest, and therefore a different tree root and a different signed object, for the identical logical document; this was flagged as a fatal cross-implementation-divergence finding against the pre-repair draft. Closed by naming `ABSENT_CHILD_DIGEST = SHA-256(0x00)` as a reserved, permanent constant, paired with domain-tag separation across all four preimage classes (`0x00` reserved for the filler, `0x01` internal T_S nodes, `0x02`/`0x07`/`0x08` for T_C redactable leaf / non-redactable leaf / internal node respectively) so no real digest preimage can ever collide with the filler or with another class's leaves.
2. **T_C's leaf-tag reuse.** An earlier draft used the same domain tag for redactable leaves and for internal nodes, with no arity, length, or depth encoded into the internal-node preimage; an attacker could choose a redactable leaf's salted plaintext so that its digest is bit-identical to a crafted internal node's digest, giving two structurally different content trees the same root, a classic Merkle tree-shape second-preimage (the same shape RFC 6962 and the Bitcoin CVE-2012-2459 both exist to prevent). Closed by the 4-way domain-tag separation above.

### The signed object, and why "sign the whole canonical octet stream" was rejected

An earlier, simpler construction (`signed_object = a single digest over the whole canonical octet stream`) was tried and rejected across two independent architecture drafts on the same finding: a redacted document does not contain the omitted subtree's octets, so no verifier can ever recompute that whole-stream digest for the signed state once a designated subtree has been removed, which makes the `attested-with-declared-omissions` verdict FR-076 requires structurally unreachable, every redacted document collapsing to the same `unverified` result whether the omission was declared or not.

**Chosen:** `signed_object = H(0x04 || T_C_root || structure_digest || presentation_artefact_digest || coverage_descriptor_digest)`, signing `T_C_root` directly rather than a flat stream digest, so redaction removes octets from the tree's leaves without changing what the signature covers at the leaves that remain. `structure_digest` is redefined in Repair Set 2 to be a sorted vector over only the *covered* ordinals' `(ordinal, type, length, digest)`, with every digest recomputed fresh from the file's actual current octets at verify time, never read from a stored slot; this closes two problems at once. First, it makes `structure_digest` placement-insensitive for uncovered segments, which is what makes the new **partial compaction** operation safe: an explicit operation that may relocate or reclaim only segments named in no signature's covered ranges, leaving covered segments' ordinals, offsets, lengths and digests byte-identical, resolving the "MAX_SEGMENTS ceiling bricks a signed document" residual risk for the common case of a signature that does not cover 100% of the document (see Section 8 for the case it does not resolve). Second, "recomputed fresh, never trusted from a stored slot" closes the class of bug where a verifier accepts an attacker-forged inventory because the inventory agreed with its own stored digest of itself; TR-009's forged-inventory detection depends on this.

### Ed25519 verification: from an unimplementable label to a closed 7-step procedure

An earlier draft's allowlist entry named Ed25519 verified via "a ZIP-215-style, cofactored, batch-compatible procedure with mandatory rejection of non-canonical encodings and small-order keys." This was refuted on two independent grounds. First, ZIP-215's entire purpose is to *accept* certain non-canonically-encoded and small-order inputs that other verifiers reject, which is the opposite of "mandatory rejection" in the same sentence; the two halves of the label describe mutually exclusive verification equations. Second, and more decisively, this project's constitution (CP-010) restricts the verify path to the Go standard library, and `go doc crypto/ed25519` against the actual installed Go 1.25.1 toolchain confirms that `VerifyWithOptions`'s `Options` type exposes only `{Hash, Context}` (for selecting Ed25519ph/ctx); there is no lever anywhere in the standard library to choose cofactored versus cofactorless verification, or to select which of the several documented, mutually divergent EdDSA verification equations catalogued in the "Taming the many EdDSAs" literature gets run. A design that claims a specific named procedure while being restricted to an API that cannot express that procedure was, correctly, judged unimplementable as written, not merely under-specified.

**Chosen: EdDSA-Protodoc-1**, a closed 7-step wrapper, confirmed against the actual installed toolchain, that pre-filters exactly the inputs where implementations are documented to diverge using cheap, curve-arithmetic-free integer and byte comparisons, then delegates the uncontested remainder to unmodified stdlib: (1)-(2) decode and reject non-canonical or small-order `A` by plain comparison against `p = 2^255 - 19` and a fixed 8-element low-order-point table (Curve25519's order-8 torsion subgroup has exactly 8 elements); (3)-(4) identical checks on `R`; (5) reject `S >= L` where `L = 2^252 + 27742317777372353535851937790883648493`; (6) compute the challenge `k = SHA-512(R || A || msg) mod L` via stdlib `crypto/sha512`; (7) delegate the actual curve-arithmetic equation to unmodified stdlib `crypto/ed25519.Verify`, now only ever invoked on inputs where Go's internal behavior cannot diverge from strict RFC 8032. Roughly 60-100 new lines, 100% stdlib (`math/big` or plain byte comparison, `crypto/sha512`, `crypto/ed25519`). Rejected alternative: hand-rolling full Edwards-curve point decoding, doubling and scalar multiplication in reviewable Go, which closes the same gap at an estimated 400-600 lines for no additional correctness benefit once the pre-filter already removes every documented divergence source. Also rejected, as before: RFC 6979 deterministic ECDSA (deterministic, but `crypto/ecdsa` in the Go standard library signs with a hedged, rand-reader-mixed nonce and is not bit-reproducible; implementing RFC 6979 by hand would add roughly 200-450 lines of new cryptography to a core path for zero benefit over a scheme that is deterministic by construction and already in the standard library) and deterministic RSA (deterministic and in the standard library, but costs signature and key size against a format with hard prefix octet budgets, for no benefit over Ed25519).

### Redaction: the salt-inside-the-subtree construction, kept; the severed-state digest conflict, not resolved

**Chosen and unchanged across every repair round:** at signing time, the signatory designates content subtrees as redactable; each is committed with `H(0x02 || salt || canon(subtree))`, with the 32-octet salt stored *inside* the subtree it commits. Removing the subtree removes the salt with it, so the retained parent commitment cannot be opened by exhaustive search short of 2^256 work, comfortably above FR-075's 2^80 floor. This construction is convergent across every architecture draft that scored above `fatally-flawed` on the adversarial lens and is treated as settled.

**Not resolved, flagged explicitly rather than designed around:** FR-061 requires a document to enumerate "the identifier and digest of every previously published state it can no longer reconstruct," in language that, read literally, calls for a bare, unsalted digest. Because that digest is unsalted, it is a brute-force dictionary oracle over exactly the class of content (names, dates, amounts) that FR-075 spends 256 bits of salt to protect against the *identical* attack in the redaction path; implementing FR-061 literally reopens, for trimmed history, the exact privacy hole FR-075 exists to close for redaction. This plan ships the salted-commitment form (`severance_commitment = H(severance-domain-tag || severance_salt || state_digest)`, salt destroyed at trim) as its answer, but this is a normative change to FR-061's literal text, not something the currently-approved spec authorizes, and it is recorded in `spec.md`'s conflict list for Eyvar/themis to rule on before phase 5 (analyze) closes. See Section 8, item 1.

### Coverage circularity (TN-008) and the ATTEST-type exclusion

FR-002 defines the acted-upon set as every octet that can influence extraction, rendering, validation verdict, or reported metadata, and requires every signature to cover it totally or enumerate the uncovered remainder. Signature components themselves influence the validation verdict by this same wording, so they belong to the set they must be covered by, a circularity. Closed by categorically excluding every ATTEST-typed segment (signatures, time attestations, severance/rescind records) from every signature's coverable set, including a signature's own bytes and every other co-existing signature's bytes; the 6 losing commit-ring slots are excluded the same way. This closes the circularity by construction rather than by a carve-out that itself needs policing, which was the specific weakness found in at least one rejected architecture's version of the same idea (an unsigned "acted-upon set defined by reachability from the very record the attacker controls" argument, which is circular in a way this exclusion is not, because ATTEST-type membership is a fixed, structural property of a segment's type tag, not a claim about reachability from a mutable pointer).

## 6. History and merge

### History storage: one representation for three modes, chosen; the trim-privacy conflict inherited from Section 5

CQ-008/CON-022 require exactly three history modes (complete, retained-from-a-point, none), declared immutably at creation, sharing **one** representation (CON-005 forbids a second construct for the same capability). **Chosen:** typed HISTORY segments of RLE-batched operations plus a `retention_point` ordinal in the commit ring; a lawful in-place trim zeroes pre-point segments, leaving the enumeration described in Section 5.

Rejected alternatives:
- **Append-only hash-chained operation log as the sole structure.** Rejected because trimming the head of a hash chain destroys the cryptographic integrity of the tail; there is no way to sever the past without also severing the verifiability of everything after it, which makes CQ-008's mandatory lawful-trim path unimplementable for any mode that needs to retain a suffix.
- **State-delta chain, each state a diff against its immediate predecessor.** Rejected for the identical reason: a trim severs every later state's ability to reconstruct itself.
- **Full snapshots at every published state with structural sharing by content address.** Considered and partially adopted in spirit (a materialized current state is kept separate from the append-only history region specifically to satisfy NFR-033's 1.5x load-time-and-memory ratio at a tenfold operation-count difference), but full per-state snapshotting alone, without RLE batching of the operation log, was shown to miss NFR-032's 2.0x at-rest ratio at the spec's own 250,000-operation benchmark scale by roughly an order of magnitude when the corpus's actual op-to-character ratio (2.5 operations per final character, a fragmentation-heavy pattern) is used rather than a favorable long-run-length case.

### Merge: from an unsupported "generalized FugueMax" assertion to a closed 4-way classification

The pre-repair draft's answer to HC-026 (zero implementation-defined outcomes across every pair of concurrent operation kinds) was to assert that Fugue's published non-interleaving proof, established specifically for text-sequence insertion, "generalizes" to every operation kind in the document's data model (structural moves, table row/column operations, property sets, renames, resizes, annotation creation) via a single commit-level `state_id`-lexicographic tie-break, with an actual worked rule given only for the move-cycle case. This was refuted directly: Fugue's proof does not cover non-text operation kinds, no pairwise resolution table was ever given for the dozen-plus operation kinds and dozens of resulting pairs, and a commit-level key cannot by itself decide the relative order of two different authors' *characters* both inserted immediately after the same anchor within one delivered batch, which is exactly the case FR-093's 1,000-trial test exercises. This claim is recorded in Section 8's unsupported-claims list from the refutation record and is not re-asserted here as settled without the fix below.

**Chosen: an exhaustive, kind-based 4-way classification requiring no per-pair table at all**, because every operation in the data model is, by its own definition, exactly one of three primitives: a position-claim, a value-claim, or a delete. (0) **DISJOINT-COMMUTE**: non-overlapping targets, apply both, the majority of real pairs. (1) **R1 SEQUENCE-ORDER**: Fugue's actually-proven non-interleaving order, applied only to genuine sequence-insertion operations (text, table row/column insertion, extension-envelope insertion, annotation creation, including a comment's own text body, which is itself an ordinary text block), where the proof applies directly because each of these literally is a sequence insertion, not an analogy to one. (2) **R2 TOTAL-ORDER-TIEBREAK**: for any two operations setting the *same* single-valued field of the *same* unit (a property, a rename, a non-cycle move, a resize), resolved by comparing `state_id` as unsigned big-endian octets, smaller wins, the same rule already used for move-cycles, now applied uniformly. (3) **R3 DELETE-DOMINATES**: a delete concurrent with anything else targeting the same unit; the delete applies, and the other operation's disposition is read from a fixed, per-kind table of no-op versus orphan-carry, never invented ad hoc at merge time. Because every operation kind is exhaustively a position-claim, a value-claim, or a delete by construction, this 3-primitive-plus-default partition covers every pair among every operation kind without enumerating pairs, closing HC-026's zero-implementation-defined-cells requirement structurally rather than by table maintenance. This remains an addition made in this repair pass, not yet exercised against a property-based adversarial corpus; see Section 8, item 9.

### Sequence-merge CRDTs rejected wholesale

- **RGA (Replicated Growable Array).** Published work demonstrates character-by-character interleaving of concurrently-inserted passages, failing FR-093's unbroken-substring requirement; additionally retains deleted characters as tombstones in the live structure, which would leak into published output and fail FR-078's octet-level residue search.
- **Logoot / LSEQ.** Same interleaving failure under reverse-direction (backspace-style) concurrent insertion even in the improved dense-identifier families; additionally, their dense fractional position identifiers are themselves persisted, ordered, counted positions, independently banned by FR-025/CON-001 (see Section 4).
- **Treedoc, WOOT.** Same tombstone-retention failure against FR-078/HC-019 as RGA; these families were not separately evaluated for interleaving because the tombstone failure alone is sufficient rejection.
- **Operational transformation without a specified total order.** Rejected because OT's correctness depends entirely on the specific transformation functions and their composition rules being proven for the exact operation set in use; no such proof exists for this document's operation-kind set (structural moves, table axes, extension envelopes are not part of any published OT proof this research considered), and adopting OT wholesale would only relocate the same "the proof does not cover this case" gap the merge classification above closes directly.
- **Last-writer-wins by timestamp.** Rejected independently by NFR-005, which bans any value derived from wall-clock time from participating in the persisted octet stream outside the four permitted non-deterministic sites (identifier minting, redaction salts, signature values, timestamp attestations), none of which is "an ordinary merge tie-break."

Things considered and dropped entirely, not merely as one candidate among several, with the reason each was dropped:

| Item | Why dropped |
|---|---|
| **Zip-of-parts container** | Fails six independent hard constraints simultaneously (HC-005, HC-006, HC-003/004, HC-012, HC-002, HC-015); see Section 2. No restricted profile survives all six without ceasing to be zip. |
| **Protocol buffers as the wire encoding** | Eleven independent, documented failure points, three of them (nested-message containment, allocate-before-validate parsing, shared-schema-defeats-CP-003) structural rather than fixable by profile; see Section 3. |
| **AV1-intra-only as the single lossy raster codec** | CP-003 requires two implementations sharing no source code. A bit-exact AV1-intra decoder is estimated at 12,000-20,000 lines, the largest single component in the reference implementation by a wide margin. That forces a choice between both implementations binding an existing decoder (which shares the actual decode logic and defeats the point of independent conformance for exactly the component most likely to hide spec ambiguity) or two from-scratch, research-grade codec efforts with no credible schedule against NFR-027's 30-working-day rendering budget. **Replaced in Repair Set 2 by PLP-1**, a from-scratch, exactly-specified, roughly 480-decode-line codec (fixed 8x8 blocks, one of 8 normative fixed quantization matrices, fixed canonical-Huffman entropy tables with no per-image optimization, DC-DPCM, an integer-matrix-plus-fixed-point-shift-schedule IDCT borrowing only AV1/HEVC's "the integer transform is the specification" pattern and none of their surrounding codec machinery, fixed-point integer YCbCr-to-RGB, 4:4:4 only, intra/single-image only). Only decode need be bit-exact; the encoder is writer-discretionary. |
| **Baseline JPEG** | Its inverse DCT was specified only to an IEEE 1180 statistical accuracy envelope (since withdrawn), so conforming decoders legitimately drift from each other, which is precisely the decoder-drift failure mode NFR-019's zero-tolerance raster-equality requirement exists to exclude. |
| **VP8 / WebP** | Bit-exact per RFC 6386, but RFC 6386 defines parts of decode by reference to its own C source code, which is a CON-006/CP-009 violation on its face (no normative statement may be defined by reference to a named application or codebase) unless a genuinely independent, from-scratch prose re-specification is written, which was judged as large an undertaking as writing a new codec from scratch. |
| **JPEG XL** | Specifies parts of its decode path in floating point, incompatible with zero-tolerance bit-exact decode across independent implementations. |
| **HEVC** | Bit-exact transform precedent is real and partially borrowed (see PLP-1's IDCT), but the full codec's patent licensing terms were judged incompatible with CP-014's requirement for an irrevocable, royalty-free grant; AV1's own royalty-free grant was one reason it was tried first before being rejected on line-count grounds above. |
| **Full-face font embedding (no subsetting)** | Works against NFR-024's font-less-durable-profile raster-equality requirement and the format's general resource-budget discipline; subset embedding with the mandatory 7 recorded values per font (FR-089) was chosen instead. |
| **Page-oriented store with a page table and free list (SQLite/ext-style)** | See Section 2; free-list residue and content-triggered page relocation both violate hard constraints directly. |
| **Trailing index / trailing central directory, appended per save** | See Section 2; violates TR-006/007/008's bounded-prefix determinations regardless of container family. |
| **Digest-sorted or hash-bucketed physical storage placement (git-style tree ordering)** | Explicitly forbidden by CQ-007 and FR-058: if physical placement is a function of content, changing one unit's content relocates its extent and shifts every following one, which is the exact whole-file-rewrite-on-edit failure the ledger design exists to avoid. Content addressing is kept for deduplication and integrity; placement is a content-independent monotonic ordinal instead. |
| **BLAKE2b / BLAKE3 for structural digests** | Confirmed to live in `golang.org/x/crypto`, a separate module from Go's core standard library (an open upstream proposal to migrate it into the standard library is unresolved as of this writing), so adopting it in a core parse/validate/canonicalize/verify/extract path would violate CP-010's standard-library-only mandate. SHA-256 (`crypto/sha256`, confirmed in the standard library) is used for every structural digest instead; SHA3-256 (`crypto/sha3`, also confirmed present in the installed Go 1.25.1 standard library) is reserved exclusively for the outer re-protection layer, chosen specifically because it is a structurally independent hash family from SHA-256. |
| **A post-quantum signature scheme in the v1 allowlist** | Go 1.25's standard library ships `crypto/mlkem` (a key-encapsulation mechanism) but no post-quantum signature scheme (no ML-DSA), so no stdlib-only PQ signature path exists today. Not solved by this plan; instead, a new **RESCIND-AND-RESIGN** operation is introduced, available only at a major-version migration boundary, letting a custodian add a signature under a new allowlist scheme over migrated content while the old signature and its metadata remain in the already-mandatory retained pre-migration state, giving an auditable two-scheme custody chain if Ed25519/Curve25519 itself, not just a hash, is ever broken. This is distinct from CON-016's existing hash-only re-protection layer, which only helps against hash weakening, not scheme weakening. The residual exposure (a document signed only under Ed25519 that is never migrated before the scheme breaks has no protection, because the mechanism is not self-triggering) is disclosed, not hidden; see Section 8. |
| **RFC 6979 deterministic ECDSA, deterministic RSA** | See Section 5: both are deterministic and viable in principle, but Ed25519 via the standard library achieves the same determinism property with less new code and no hand-rolled cryptography in a core path. |
| **A single Merkle tree serving both storage integrity and content redaction** | Considered directly (forcing storage extents to be subtree-aligned to the content tree so one structure serves both jobs) and rejected because it would make storage placement a function of content-tree structure, breaking FR-058's placement-independent-of-content rule the moment the content tree is restructured. |
| **buf as a toolchain dependency** | Moot: the byte encoding is not protobuf (Section 3), so there is no `.proto` schema for `buf` to operate on. `buf` was confirmed not installed on this machine and is not required by any chosen mechanism in this plan. |
| **Converters and the live collaboration engine as v1 scope** | CQ-011 places both off the v1 critical path; this plan does not design either. Recorded here so a future contributor does not re-propose adding them to phase 4's task list without first reopening CQ-011, which is outside this phase's authority. |

## 8. Open technical questions

What this phase could not settle, stated as a question, with the evidence available and what would resolve it. None of these are silently designed around; each is either a flagged spec conflict awaiting Eyvar/themis ruling, a governance decision outside architectural authority, or a residual risk carried forward with its mitigation stated honestly.

1. **FR-061 (severed-state enumeration) versus FR-075 (2^80 redaction-hiding floor).** FR-061's literal text calls for a bare, unsalted digest per unreconstructable published state; because it is unsalted, it is a brute-force dictionary oracle over exactly the low-entropy content (names, dates, amounts) FR-075 spends 256 bits of salt to protect against the identical attack in the redaction path. This plan ships the salted-commitment form as its answer, but that is a proposed amendment to FR-061's text, not something currently approved. **Resolves when:** Eyvar/themis rules whether FR-061 is amended to require a salted commitment (this plan's position) or is read as intentionally weaker than FR-075 for the trim case specifically (and if so, why that asymmetry is acceptable). Recorded in `spec.md`'s conflict list.
2. **CON-006 (no normative statement defined by reference to a named application) versus CQ-006 option B (a named, versioned shaping algorithm implementation pinned as the normative rendering oracle).** CQ-006's own resolution text acknowledges this sits "close to the boundary CON-006 draws." This plan records the required one-time exception (EX-001) under constitution amendment rule 6, naming the principle, the reason, and an expiry condition (superseded when a normative from-scratch Protodoc shaping specification is adopted, or when milestone M-SHAPE passes the two-implementation gate), but granting that exception is a governance action outside this plan's authority. **Resolves when:** Eyvar approves or rejects EX-001; until approved, `A-VENDOR` (the automated named-application-reference audit) blocks every release.
3. **NFR-030's literal 4x-input-memory bound is unsatisfiable by any real process.** No Go binary can hold four octets of resident memory for a one-octet input; the runtime and stack alone occupy megabytes. This plan reads the requirement as bounding heap allocated for document data specifically, with an implicit floor exemption below 1,048,577 octets, and marks compliance against that reading, not the literal text. **Resolves when:** the requirement text is corrected explicitly, or an explicit floor exemption is added to spec.md; until then, CP-012's fuzzing oracle (which fires on any input exceeding 4x its own size in peak memory) will trip on every small, entirely valid input unless the harness itself encodes the same reading.
4. **NFR-027's 30-working-day rendering-role budget, specifically for shaping.** This plan's codec swap (AV1 to PLP-1) and rasterizer specification cut the credible rendering-role estimate from an original 60-200+ days to roughly 28-49 days, but the residual overrun is now concentrated almost entirely in the shaping sub-component, which is an oracle-matching effort against a pinned external implementation (CQ-006 option B), not a lines-of-code task, and is estimated at 15-25 days on its own. **Resolves when:** Eyvar/themis makes an explicit scope decision for the shaping share of the budget specifically (per the precedent in `clarify.md`'s AD-002: "the correction is a scope decision under CP-002, not a silent re-tiering"), rather than the whole rendering role's budget being treated as uniformly at risk.
5. **FR-055's read-count clause versus its octet-ceiling clause.** One sentence covers both "at most 3 sequential dependent reads to locate and read" a unit and "no more than [budget] octets beyond the unit itself." A reading that lets the octet clause's "beyond the unit itself" exclusion also narrow the read-count clause can undercount the hop budget by one, and the chosen prefix-plus-index-plus-unit design (3 total reads including the final read of the unit) only closes under the stricter reading (the read-count clause's "and read" phrase includes the final read). **Resolves when:** the requirement text is split into two independently-scoped sentences for future implementers who have not seen this analysis.
6. **The CQ-012/CP-003 two-independent-implementation gate may never be cleared for lack of an incentive, not for lack of a specification.** Every fix in this repair pass makes the second implementation's job more tractable (closed TLV grammar, a 7-step Ed25519 procedure instead of an ambiguous label, a ~480-line codec instead of a 12,000-20,000-line one), but none of it manufactures a reason for an independent second team to spend the estimated weeks-to-months building a reader for a zero-adoption, unstandardized format with no legacy corpus and no paying customer requiring interoperability. **Resolves when:** Eyvar decides, before phase 5 (analyze) closes, on an explicit adoption or funding strategy (a commissioned or sponsored second implementation, a standards-body submission, or a scoped-down rendering role a volunteer could plausibly finish quickly) so that CQ-012 is treated as a reachable milestone rather than an aspiration. This is a programme-management question, not an architectural one; no design change in this plan can manufacture the incentive.
7. **TOTAL-mode signature coverage gets no benefit from partial compaction.** Repair Set 2's partial-compaction mechanism resolves the segment-ceiling bricking risk for any signature whose `coverage_descriptor.mode = SUBSET`, but a signature whose mode is `TOTAL` covers everything by definition, so there is nothing uncovered to reclaim; the original roughly-58-day exhaustion under continuous autosave remains exactly as severe as before this repair pass for that specific, disclosed case. **Mitigation carried forward, not a fix:** a distinct refusal status names the ceiling and observed segment count; tooling guidance treats a TOTAL-mode signature on an actively-edited document as a documented anti-pattern, recommending SUBSET-mode coverage (covering exactly the substantively-signed content, leaving ongoing commentary or draft churn uncovered) for any document expected to undergo continued heavy editing after signing.
8. **PLP-1 is a from-scratch, previously unbuilt, unbattle-tested codec.** Being small and exactly specified removes the CP-003 infeasibility that killed AV1, but it is new code with no deployment history; an undiscovered bitstream ambiguity or an off-by-one in the fixed-point IDCT shift schedule could exist despite the small size, and would only surface once two independent implementations are actually built and compared. **Resolves when:** exhaustive decode conformance vectors (every fixed quantization matrix, every Huffman table branch, boundary block sizes, worst-case DPCM chains) are authored as a first-implementation activity in phase 6, not an afterthought.
9. **CoverageDescriptor's merge-adjacent canonicalisation and the R1/R2/R3 merge classification are both new normative surfaces introduced in this repair pass, untested against any adversarial or property-based corpus.** Each is fully specified (an exact comparator, an exact classification rule) but neither has been exercised against real inputs, so an edge case such as a range list at exactly the MAX_SEGMENTS boundary, or an operation kind that does not cleanly fall into one of the three merge primitives, cannot be ruled out. **Resolves when:** `tasks.md` includes, as first-class tasks rather than folded into general conformance work, a dedicated property-based fuzzer for CoverageDescriptor range-list canonicalisation and a dedicated exhaustive-pair test asserting every operation kind in the actual schema resolves to exactly one of `{DISJOINT-COMMUTE, R1, R2, R3}` with no fourth case ever reached.
10. **Whether PDL's selection over Slab-DAG at a tied mean score (4.67 each, zero fatal findings on either side) rests on a recorded rationale beyond the graft record.** This phase's evidence shows PDL absorbing Slab-DAG's coverage-by-construction mechanism and shows Slab-DAG's own equivalence-class self-contradiction as a genuine, if repairable, weakness, but does not contain an explicit document stating "PDL over Slab-DAG because X." **Resolves when:** the decision record from whichever earlier session made this selection (Repair Set 1 or before) is located and appended here, or, absent that record, this is treated as settled by precedent (the `final_architecture.chosen_base` field is authoritative) and not reopened without Eyvar's explicit instruction, per the SDD rule that phase 3 does not reopen a decision it did not itself make.
11. **Several adversarial findings against PDL's own draft (not against a rejected competitor) remain without an explicit, named fix in the current architecture text**, specifically: the frame-directory offset arithmetic (`segment_offset + segment_length - (frame_count*48 + 32)`) has no stated invariant bounding `frame_count` against `segment_length`, which permits an unsigned-subtraction wraparound at the stated ceiling; the extension envelope's `fallback_ref` is not listed among FR-109's five enumerated cycle-detection edge kinds, which permits an undetected fallback-reference cycle; and FR-053's preview-staleness check depends on a digest over render inputs that live past the 262,144-octet window the check is scoped to, making the check unrecomputable by the bounded-prefix consumer it exists for. **Resolves when:** phase 4 (tasks) either names the specific fix for each (a stated `frame_count * 48 + 32 <= segment_length - 64` bounds check; adding `fallback_ref` as a sixth cycle-detection edge kind; rescoping FR-053's digest to cover only in-window fields) or these are explicitly re-flagged as accepted residual risk with the same honesty this plan applies elsewhere.
