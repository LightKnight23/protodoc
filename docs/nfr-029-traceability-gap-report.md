## Two items needing an explicit ruling, not just more implementation

These two are flagged separately because no amount of future implementation work resolves them by
itself -- they are disagreements about the *identifier registry itself*, which CP-011's own
consequence clause says a person must never resolve by silent edit ("rule identifiers are never
renumbered or reused").

### 1. Sixteen of eighteen spec-named `PD-*` rule ids never reappear in the wire-grammar contracts

`spec.md` names 18 distinct validator-rule ids in its own prose (`PD-NFC-002` and the historical
`PD-NORM-001` it replaced, `PD-SCALAR-001`, `PD-DUP-001`, `PD-MODE-001`, `PD-EXT-001`,
`PD-EXT-002`, `PD-EXT-003`, `PD-LANG-001`, `PD-BIDI-001`, `PD-A11Y-001..004`, `PD-PREV-001`,
`PD-TBL-001`, `PD-FONT-001`, `PD-2D-001`, `PD-INFER-001`). Of these, only **`PD-EXT-002`** and
**`PD-MODE-001`** also appear in `contracts/*.abnf` (in `document.abnf` and `container.abnf`
respectively) -- the file that is supposed to be each rule's normative wire-grammar definition.
The remaining 16 exist only as a name in spec.md prose, with no corresponding ABNF rule anywhere.
Both of the two that do reappear are, independently, still conformance-coverage gaps below (no
implementation exists yet for extension or mode-signalling records), which is expected at this
stage; the 16 that never reappear in the contracts at all are a different, structural problem no
future test can fix on its own -- the contracts need the missing rule definitions written first,
by a ruling on what each rule is actually meant to check.

### 2. `PD-NORM-001` was silently renamed to `PD-NFC-001`/`PD-NFC-002`

`spec.md`'s own CON-002 prose (the Unicode Normalization Form C requirement) states, in its
Verify clause: "Validator rule PD-NFC-002 (renamed from an earlier draft's PD-NORM-001 at phase 5
analyze; contracts/document.abnf and data-model.md already used PD-NFC-002, per Eyvar's ruling
that the contracts/data-model naming is canonical)". That parenthetical claims a ruling by Eyvar
already happened. **No such ruling is recorded anywhere in this repository** -- not in
`clarify.md`'s resolved `CQ-001`..`CQ-017` list, not in `analysis.md`, not in any commit message.
CP-011's consequence clause is explicit that "rule identifiers are never renumbered or reused", with
no exception carved out for a rename made consistent after the fact. Whoever wrote that
parenthetical into spec.md's prose was not authorized to assert Eyvar's approval on Eyvar's behalf,
and this report does not repeat that assertion as fact: it surfaces the rename and the unrecorded
approval claim together, for Eyvar/themis to actually rule on (accept the rename as CON-002's
canonical id and correct spec.md's own text to stop calling it a "draft" name, or reject it and
require `PD-NFC-001`/`PD-NFC-002` to be retired back to `PD-NORM-001` throughout `contracts/` and
`data-model.md` instead). Both `PD-NORM-001` and `PD-NFC-002` are listed as separate rule-id gaps
below, deliberately not merged into one, because they are exactly the two names this ruling must
choose between.

## Release-gate mechanism

`TestNFR_029_AllNormativeStatementsHaveConformanceCase` runs this same audit at test time. In a
normal development run it never fails the build on gap count alone (this repository is
mid-implementation; failing every `go test ./...` invocation on 114 known, tracked gaps would
make the signal useless). It always fails, in every run, if this checked-in file's own enumerated
gap list has drifted from what a live audit currently finds, so this report cannot silently go
stale. Separately, when the environment variable `PROTODOC_RELEASE_GATE` is set to a non-empty
value, the same test additionally fails on every remaining gap, individually, by id -- this is the
literal mechanism by which "a release SHALL be blocked while any normative statement has zero
mapped cases": a release process that does not set `PROTODOC_RELEASE_GATE=1` and see that test
suite pass has not satisfied NFR-029, regardless of what else it checked.
